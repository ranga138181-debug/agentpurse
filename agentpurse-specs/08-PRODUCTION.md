# 08 — Production

Version 1.0 · 9 Oct 2026

## Assumptions

1. Hosting is Render: one Node web service and one Render Postgres database, defined in a `render.yaml` blueprint in the repository.
2. "Production" means the public demo. It still uses the PayPal **sandbox**.
3. Render plan behaviour (idle spin-down on free web services, time limits on free Postgres) must be checked on Render's current pricing page during M1. The instance and database must stay available without cold starts from 6 Nov until judging ends; choose the plan accordingly.
4. The repository is public on GitHub from the first commit, with the MIT licence.
5. Trunk-based development: short-lived branches, pull requests into a protected `main`.

## 1. Environments

| Environment | Purpose | Database | Model | PayPal | Catalog |
|---|---|---|---|---|---|
| Local | development | local Postgres | `fake` by default | fake client in tests; sandbox when run manually | fixture |
| CI | automated tests | Postgres service container | `fake` (real for eval job) | fake client (IT), sandbox (IT-PAY-010, E2E) | fixture |
| Production | public demo and judging | Render Postgres | real provider | sandbox | fixture, or Channel3 if FR-026 ships |

Configuration is by environment variables only (`02-ARCHITECTURE.md` §9). The app validates them at startup and exits on error.

## 2. Hosting

- **Web service:** Node, build with the framework's production build, start with the production server. Health check path `/api/healthz`. Region closest to the database.
- **Database:** Render Postgres, same region, connection over the internal URL.
- **Migrations:** forward-only SQL migrations generated by Drizzle Kit and committed. They run before the new version starts serving (Render pre-deploy command where the plan supports it, otherwise as the first step of the start command). A failed migration fails the deploy.
- **Migration rule:** each migration must be compatible with the previous application version (add before use, remove after unused), so an application rollback never needs a schema rollback.
- **Warm instance:** the service must not spin down during the judging period (Assumption 3).
- **Auto-deploy from Git is off.** Deploys are triggered only by the pipeline.

## 3. CI/CD (GitHub Actions)

### 3.1 `ci.yml` — on pull request and on push to `main`

| Job | Steps | Gate |
|---|---|---|
| `lint` | install, ESLint, Prettier check | G1 |
| `typecheck` | `tsc --noEmit` | G1 |
| `unit` | Vitest unit tests with coverage; fail if `src/policy` branch coverage < 100% | G2, G3 |
| `integration` | Postgres service, migrations, Vitest integration tests | G2 |
| `secret-scan` | gitleaks GitHub Action over the full history | G4 |
| `build` | production build | – |

All six are required status checks on `main`. Direct pushes to `main` are blocked.

### 3.2 `e2e.yml` — on push to `main`, nightly, and manual

Builds the app, starts it against a CI Postgres with `AI_PROVIDER=fake` and PayPal sandbox secrets, and runs Playwright. Uploads traces and screenshots on failure. Also runs IT-PAY-010.

### 3.3 `deploy.yml` — after `ci.yml` and `e2e.yml` succeed on `main`

1. Trigger the Render deploy hook for the commit.
2. Poll production `/api/healthz` until it reports the commit SHA (timeout 10 minutes).
3. SMOKE-001. On failure, the job fails and the rollback procedure in §6 applies.

### 3.4 `eval.yml` — manual only

Not scheduled: one eval run uses about a quarter of the model provider's free daily token allowance, which the public demo shares.

Runs the 30-mandate eval in CI with the real model and a fixed clock (`07-TEST-PLAN.md` Assumption 4) and computes the §6.3 gates. Then runs PERF-001 against production. Uploads both reports as artifacts. A manual run can also start REL-001, which repeats E2E-001 twenty times against production and requires at least 19 to settle. Not a required check on pull requests (it costs model calls and is not deterministic).

### 3.5 Secrets in GitHub Actions

`PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, sandbox buyer email and password, `AI_API_KEY`, `RENDER_DEPLOY_HOOK_URL`. Workflows triggered from forks do not receive secrets; jobs that need them are skipped there.

## 4. Observability

### 4.1 Logs (NFR-005)

JSON lines to stdout, collected by Render.

| Field | Notes |
|---|---|
| `ts`, `level`, `msg` | |
| `request_id` | also returned as `X-Request-Id` |
| `route`, `method`, `status`, `duration_ms` | one line per request |
| `session_id`, `mandate_id`, `order_id` | when known |
| `step`, `attempt`, `step_duration_ms` | agent steps: `parse`, `search`, `rank`, `policy` |
| `paypal_debug_id` | from PayPal error responses |
| `error_code` | on failures |

Never logged: secrets, cookies, full mandate text at `info` level, raw model output, PayPal access tokens. Redaction rules are in `06-SECURITY.md` §4.

### 4.2 What to watch

| Signal | Source | Action threshold |
|---|---|---|
| Health | Render health check on `/api/healthz` | any failure |
| Mandate latency | `duration_ms` for `POST /api/mandates` | p95 above 8 s |
| Agent failures | count of `AGENT_UNAVAILABLE`, `AGENT_TIMEOUT` | more than 5% of mandates |
| Payment failures | count of `PAYMENT_PROVIDER_ERROR`, `ORDER_FAILED` | more than 5% of orders |
| Policy blocks at order time | `ORDER_BLOCKED` events | any `AMOUNT_MISMATCH` |
| Usage | mandates per day against `DAILY_MANDATE_CAP` | above 80% |

For a hackathon demo these are checked by reading Render logs and the audit table. No external monitoring service is in scope.

### 4.3 The audit log is not the application log

The audit log records decisions for the user and is append-only business data. Application logs are for operators and may be discarded. Neither substitutes for the other.

## 5. Release procedure

1. All release gates in `07-TEST-PLAN.md` §7 are met on the commit.
2. Merge to `main`. The pipeline deploys.
3. SMOKE-001 passes.
4. Run one manual approved purchase and one blocked attempt on the production URL.
5. Tag the commit (`v1.0.0` for the submission build).

## 6. Rollback

| Situation | Action |
|---|---|
| Deploy fails health check | Render keeps the previous version serving. Fix forward or revert the commit |
| Bad release is live | Roll back to the previous successful deploy from the Render dashboard, then revert the commit on `main` so the pipeline state matches |
| Bad migration | Migrations are backward compatible (§2), so roll back the application only. Correct the schema with a new forward migration |
| Leaked secret | Rotate at the provider, update Render and GitHub secrets, redeploy (`06-SECURITY.md` §4) |
| PayPal sandbox outage | No rollback. The app fails closed with `PAYMENT_PROVIDER_ERROR`. Retry later |
| Model provider outage | Change `AI_PROVIDER` and `AI_MODEL` in Render to another supported provider and redeploy (FR-019) |

**Freeze:** no deploys to production after 12 Nov 12:00 IST except a rollback.

## 7. Data

- No personal data is collected beyond what the visitor types into a mandate. PayPal sandbox buyer details stay with PayPal.
- The database holds demo data only. Backups are whatever the Render plan provides; no additional backup is in scope.
- The audit table is never truncated in production.
